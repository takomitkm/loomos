# 03 — OS 级工作盘点：哪些该让 OS 代劳

> **问题**：旧系统（HA4FPAI）和本原型的不少用户态机制，当年是因为
> **Ubuntu 20.04 / 厂商内核 5.4.52 缺功能**才被迫自己做的。本文逐项挑出来，
> 判定：换到「OS 已提供」的能力后哪些可以删、哪些必须保留。
>
> **事实来源**：`docs/dev/platforms/FMQL30TAI676H/07-platform-baseline.md`
> （证据等级 A=板上实测）。实施等级纪律见 `docs/dev/architecture/11 §11.3.2`。
> **判据**：一句话搬到"内核带 cgroup/namespace/LSM/SMMU 的新板"还成立吗？
> 不成立 ⇒ 这是内核缺口撑起来的用户态工作，可代劳。

---

## 0. 平台缺口速览（为什么当年要自己写）

| 内核/系统能力 | 本板现状（证据级） | 后果 |
|---|---|---|
| cgroup 控制器 | `CGROUPS=y` 但 **SCHED/PIDS/MEMCG/CPUSETS/DEVICE/CPUACCT 全未编译**（A） | 无法按服务限内存/CPU/设备访问 → 用户态记账 |
| Namespace / seccomp / LSM | **全部未启用**（A） | 无法进程级隔离 → 全 root + 用户态 Capability |
| IOMMU/SMMU | 驱动在，**DT 未布线**，无运行时 IOMMU groups（A） | DMA 无跨设备隔离 → 单 Owner + Buffer 租约 |
| 看门狗 | 驱动已编译，**DT 无节点**，无 `/dev/watchdog*`（A） | 设备挂死只能人工断电 |
| PREEMPT_RT | `PREEMPT_NONE`（A） | 无实时承诺 → 占空比/尽力而为 |
| CPU 频率/深睡 | 无 cpufreq/OPP、无深睡（A） | 省电靠用户态占空比 |
| 内存限制 | **RLIMIT_AS 可用**；systemd `MemoryMax` 是假闸门（A，11 §11.3.2） | 只能用户态记账 + rlimit |
| 实时调度 | **SCHED_DEADLINE/FIFO/RR 可用**（A，实测准入） | ✅ 这块 OS 其实有货 |

## A. 内核缺失撑起来的用户态工作 → 现在只能保留（标注切换位）

### A1. 资源记账与限额（LeaseManager / EnforcementLevel）
- **用户态做法**：`loomos-runtime::resource::LeaseManager` 记账 + Backend 如实上报
  `unsupported`；`MemoryLimit` 只记账不强制。
- **OS 对应**：cgroup v2 `memory.max / cpu.max / cpuset.cpus / pids.max / devices.*`。
- **建议**：**保留**租约语义（所有权≠限额，永不删）；限额的**强制执行**换成 cgroup 后，
  `EnforcementLevel: unsupported → enforced`（须有设置后读回证据）。代码切换位：
  `loomos-runtime/src/resource.rs` + Linux Backend（`platform/linux` feature）。

### A2. 进程/权限隔离（CapabilityStore 只是策略层）
- **用户态做法**：`loomos-runtime::capability` 用户态校验 + 全 root 运行。
- **OS 对应**：非 root 服务用户 + udev 设备 ACL（**今天可做，见 B4**）+ namespace/seccomp/LSM（要换内核）。
- **建议**：Capability **模型永久保留**（策略层，换内核也不删）；其**强制执行**逐层下沉：
  非 root → seccomp 白名单 → LSM。红线：用户态授权不能冒充内核强制（架构总纲 §1.7 原则 5）。

### A3. DMA/Buffer 跨设备隔离（单 Owner + 隔离区）
- **用户态做法**：`loomos-inference` 单 Owner + Buffer typestate + 超时隔离区；
  旧板"内核不对共享物理窗做 mmap 互斥"（A）。
- **OS 对应**：SMMU DT 布线 → IOMMU group 隔离；新内核 dma-buf fence。
- **建议**：**保留**——cache 非一致是硬件事实（IOMMU 不解决一致性），
  typestate 编码的所有权纪律与内核无关；隔离区兜底在 SMMU 落地后降级为"第二道防线"。

### A4. 省电/负载占空比（taskset + nice + SIGSTOP/SIGCONT）
- **旧系统做法**：生产链用占空比策略压 CPU（A）。
- **OS 对应**：cpufreq/OPP（板无）+ 深睡（无）→ 无 OS 可代劳。
- **建议**：**保留但限期**——占空比"难归因"是既知缺陷（architecture/11 §11.3.3）；
  B1 的 SCHED_DEADLINE 能替代其**确定性**部分，省电部分只能等 cpufreq。

## B. OS 其实有货 → 现在就该让 OS 代劳

### B1. CPU 预算准入 → SCHED_DEADLINE（板上实测可用，A）
- **现状**：`ExecutionContract.budget` 只在用户态做准入校验，没有落到内核调度器。
- **代劳**：Linux Backend 把 `CpuBudget{runtime,period,deadline}` 直接映射
  `sched_setscheduler(SCHED_DEADLINE)`——准入测试已实测通过（4×90% DL 并发，A）。
- **删减预期**：用户态预算记账只剩"审计"，准入移交给内核；占空比 workaround 退役。
- **注意**：须重验厂商 `.ko` 与 DL 任务共存（05/09 既有关注点）。

### B2. 内存上限 → RLIMIT_AS（板上可用，A）
- **现状**：`MemoryLimit` 无强制。
- **代劳**：Linux Backend `setrlimit(RLIMIT_AS)`，配合"设置后读回"证据标 `enforced`。
- **删减预期**：用户态内存记账保留为审计；越界 kill 交给内核。

### B3. 核亲和 → `sched_setaffinity`（可用）
- **现状**：`ExecutionContext.affinity` 只做子集准入校验（loomos-runtime）。
- **代劳**：Backend 直接落 `pthread_setaffinity_np`；`affinity_required` 不满足仍拒绝（11 §11.3.3）。
- **删减预期**：无——这是本来就计划的映射，补实现即可。

### B4. 服务身份非 root 化（不需要任何新内核特性）
- **现状**：全 root（A）；loomos checklist D 最后一项未做。
- **代劳**：systemd `User=`/`SupplementaryGroups=` + 设备节点 chmod（g+k 组）+ tmpfs 帧目录权限。
- **删减预期**：CapabilityStore 的"全 root 同权限"假设消失，权限检查开始有真实边界。
- **红线**：设备节点组权限只挡普通文件访问，**跨进程强制隔离仍需 device cgroup（A1）**。

### B5. 看门狗恢复（驱动在，只差 DT 节点）
- **现状**：设备挂死 → L3 人工断电（supervisor.rs 升级人工）。
- **代劳**：**补 DT 节点**（非内核改动）→ `/dev/watchdog` + systemd `WatchdogSec=`；
  L3 从"人工"变"看门狗自动重启 + 人工复核"，Supervisor 恢复等级表随之更新。
- **删减预期**：`RecoveryLevel::L3PowerCycleManual` 的"只能人工"说明改写；
  故障注入测试加一档。

## C. 不是内核缺口 → 永久保留，别想着让 OS 代劳

| 项 | 在哪 | 为什么 OS 代劳不了 |
|---|---|---|
| 原子写（tmp+replace+fsync+目录 fsync）、flock 单实例 | recorder/provider 各处 | 正确性协议，5.4 与新内核行为一致 |
| 帧五元组 + stale 判定（3s 窗） | loomos-vision frame/pipeline | "业务新鲜度"是消费侧语义，内核没有这个概念 |
| Buffer typestate（CpuOwned→…→SyncForCpu） | loomos-inference buffer | cache 非一致是**硬件**事实；与内核版本无关 |
| 单 Owner 推理编排 / 超时隔离区 | loomos-inference orchestrator | 厂商 runtime 无 cancel/并发保证（ADR-003/004），换内核也不变 |
| PAD security_calibrated / 四道闸策略 | loomos-vision + loomos-home | 安全标定是模型+场景问题，OS 给不了 |
| Desired/Applied/Outbox 配置语义 | loomos-runtime config | 业务语义，不是资源管理 |
| 同地址空间部署（省内存） | ComponentManifest.execution | 设计选择；per-process 内存可见性改善≠应拆进程 |
| Origin/无鉴权（板端 HTTP） | loomod console | 鉴权是服务层职责；kernel firewall 不是正确解 |

## D. 换内核才解锁（已留切换位，升级前先过准入）

| 解锁项 | 前提 | loomos 受益点 |
|---|---|---|
| memcg/cpu/cpuset/pids/devices 控制器 | 重编内核或换 BSP | A1 → enforced；systemd 假闸门变真闸门 |
| NAMESPACES + SECCOMP + LSM | 同上 | A2 强制层：seccomp 白名单 + AppArmor profile |
| SMMU DT 布线 | 仅改 DT | A3 可信边界收缩；误写他设备 → IOMMU fault 可恢复 |
| PREEMPT_RT | 重编 + 厂商模块兼容 | CpuBudget 语义升级为硬实时候选 |
| 看门狗节点 | 仅改 DT（**严格说今天就能做**，见 B5） | L3 自动化 |

**升级准入（architecture/09 §I 已列，引用）**：cgroup controller 开启对厂商补丁的影响、
Namespace/seccomp 编译适配、`u-dma-buf / mali / amvx` 模块重编兼容、PREEMPT_RT 与闭源模块。
每项须有：威胁模型、测试、回退方案、**目标板实测**；"配置项已启用"≠"功能已运行"。

---

## E. 一页结论

1. **立刻做**（不依赖换内核）：B1 DEADLINE 映射、B2 RLIMIT_AS、B3 affinity、B4 非 root、B5 补 DT 看门狗。
2. **保留但标注切换位**：A1/A2/A3 的强制执行层；`EnforcementLevel` 机制就是为这一天准备的。
3. **永久保留**：C 表全部——这些是**协议/硬件/安全语义**，OS 代劳不了，也不该代劳。
4. **换内核再谈**：D 表；升级本身要过 09 §I 的准入，别把"内核新"当"功能在"。
