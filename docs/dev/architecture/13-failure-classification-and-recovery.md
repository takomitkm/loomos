# 13 — 故障分级与恢复契约

> **层级**：本文是 `architecture/` 的**跨机型现行版**（编号镜像 `baseline/`）。本机型的具体读数与取舍见 `platforms/<机型>/` 下的同号文件；两者冲突时以本层为准并留记录。
>
> **文档定位**：跨机型约束与接口。本文定义**故障怎么分类、每一类能恢复到什么程度、禁止怎么写恢复逻辑**。
> **不写**：某机型的错误码、某个 `reset` API 的语义、某次挂死的具体现象——那些写在 `platforms/<机型>/`。

---

## 13.1. 四类故障（分类固定，判据由机型补）

| 类别 | 判据 | 恢复上限 | 典型表现 |
|---|---|---|---|
| **进程异常** | 进程退出／未捕获异常／自身崩溃 | 重启进程 + 回收其 Lease | 退出码非零、core dump |
| **请求超时** | 调用返回超时，但**设备状态未知** | **不得假定设备已停止** | 超时错误码 |
| **设备挂死** | 设备不再响应，进程仍活 | 由机型声明：可否 reset / 是否需断电 | 后续调用全部超时 |
| **硬件／互连故障** | 总线挂死、无 printk、整机异常 | **断电** | 串口静默、无法 ssh |

**硬约束：每一次故障必须能归因到上表某一类。归不了类＝可观测性不足，按缺陷处理，不得当"偶发"放过。**

---

## 13.2. 恢复策略的三条禁令

1. **禁止统一 `catch Exception → restart()`。**
   `baseline/03-os-runtime.md` §3.6 已写死；本文把它升为跨机型红线。不同类别的恢复动作不同，统一重启会把"设备挂死"伪装成"进程崩溃"。

2. **超时 ≠ 取消成功。**
   超时只说明"我没等到结果"，不说明"设备已停止访问 Buffer"。此时释放 Buffer 即为 use-after-free（见 `12-resource-lease-and-buffer-ownership.md` §12.4）。

3. **`reset()` API 存在 ≠ 语义已确认。**
   反汇编行为、参数取值都不等于厂商承诺。**语义未确认前不得作为正式恢复路径**；只能作为"已知会重启设备"的最后手段，且必须记录。

---

## 13.3. 恢复等级声明（每机型必填）

| 等级 | 含义 | 本机型是否支持 | 判据 | 证据 |
|---|---|---|---|---|
| **L1 进程重启** | 退出并重启该服务，回收其资源 | 机型填 | 重启后同一请求可成功 | 机型填 |
| **L2 设备 reset** | 调用厂商 reset 接口 | 机型填 | reset 后设备可重新初始化 | 机型填 |
| **L3 整机断电** | 只能人工／看门狗断电 | 机型填 | 无软件路径可恢复 | 机型填 |

**要求**：机型必须逐级说明"上一级为什么不够"，不得跳过 L1 直接宣称 L3。

---

## 13.4. 与 Orchestration 的关系

- **排队中的请求可以取消**（还没进设备）。
- **已进入同步阻塞调用的请求不能承诺及时取消**——这是多数厂商 Runtime 的现实。
- 因此 API 语义必须区分：`cancelled_before_start` ／ `timeout_unknown` ／ `completed`。

**禁止**把 `timeout_unknown` 报成 `failed`——前者意味着资源可能仍被占用，后者意味着已释放。

---

## 13.5. 可观测性要求（跨机型）

| 要求 | 判据 |
|---|---|
| 故障可归因 | 每条故障日志能映射到 §1 的某一类 |
| 恢复动作可追溯 | 记录了"做了什么等级的恢复"及结果 |
| 资源回收可确认 | 恢复后 Lease 状态可查，不是"应该回收了" |
| 不得静默降级 | 恢复失败必须上报，不得 fallback 后当成功 |

---

## 13.6. 各机型适配表（必填）

| 项 | 要求 |
|---|---|
| **错误码映射** | 本机错误码 → §1 四类 |
| **恢复等级声明** | §3 表逐行填 |
| **危险操作限制** | 哪些恢复动作禁止在普通测试中注入（挂死类） |
| **实测证据** | 每级恢复至少一条真实读数或明确标"未验证" |
